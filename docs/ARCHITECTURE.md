# معمارية النظام — الإصدار 0.2.1

> المرجع التقني المعتمد لإعادة البناء: **[docs/SYSTEM_SPECIFICATION.md](SYSTEM_SPECIFICATION.md)**. يوضّح هذا الملف البنية والقرارات العامة، بينما يحتوي المستند المشار إليه على المخطط الكامل وكل المسارات والخوارزميات وقوائم التحقق.

## 1. نظرة عامة

تطبيق ويب أحادي المحل (single-shop) بواجهة عربية RTL، مبني كـ monorepo بثلاث حزم رئيسية:

```
المتصفح
  │  HTTP (same-origin /api)
  ▼
Vite dev server :5173  ──proxy /api──▶  Express API :4000  ──Prisma──▶  MySQL :3306
  (React SPA)                            (REST + sessions)            (gold_pos)
```

في الإنتاج تُبنى الواجهة إلى ملفات ثابتة، ويُقدَّم الـAPI منفصلاً (أو خلف reverse proxy واحد يوجّه `/api` إلى Express).

## 2. الحزم والمسؤوليات

| الحزمة | المسؤولية | لا تفعل |
|---|---|---|
| `packages/pricing` | حساب الأوزان والأسعار وقواعد العيار والتقريب. TypeScript نقي بلا I/O. | لا تعرف قاعدة البيانات أو HTTP |
| `apps/api` | REST API، مصادقة وجلسات، صلاحيات، تحقق Zod، تدقيق، معاملات قاعدة البيانات | لا تحسب الأسعار بنفسها؛ تستدعي `@gold/pricing` |
| `apps/web` | واجهة React، تنسيق، حالة الخادم عبر TanStack Query، حماية المسارات | لا تعتمد على حساب مالي إنتاجي خارج معاينات الواجهة |

الفصل يضمن أن معادلة التسعير قابلة للاختبار وحدها (28 اختباراً في ملفين: محرك التسعير وتحويل العيار).

## 3. المصادقة والجلسات

- تسجيل الدخول عبر `POST /api/auth/login` بكلمة مرور `bcrypt` (cost 12).
- جلسة مُخزَّنة في جدول `Session` مع token عشوائي في كوكي `HttpOnly` + `SameSite=Lax`.
- كل طلب محمي يمر عبر middleware يقرأ الكوكي، يتحقق من انتهاء الجلسة، ويحمّل المستخدم النشط.
- `GET /api/auth/me` يعيد المستخدم الحالي أو 401.
- تغيير كلمة المرور ينهي **بقية** جلسات المستخدم عبر `destroyOtherUserSessions` ويُبقي الجلسة الحالية نشطة، أما إعادة تعيين كلمة المرور من المالك فتُنهي كل الجلسات.
- الأدوار: `OWNER` و`SELLER`. المسارات الحساسة (`/reports`, `/settings`, `/users`, فتح/إغلاق الجرد، إلغاء البيع) محمية بـ`requireRole('OWNER')`.
- حماية إضافية: `originGuard` يرفض الطلبات المعدِّلة من أصل غير مسموح، و`rateLimit` على تسجيل الدخول (30/IP و8/حساب خلال 10 دقائق).

## 4. طبقة API

### الاصطلاحات

- نجاح: `{ "data": ... }` — الأخطاء: `{ "error": { "code", "message", "details?", "requestId" } }` مع ترويسة `X-Request-Id`.
- `jsonSafe` يحوّل `Prisma.Decimal` إلى `number` و`Date` إلى ISO string قبل الإرسال.
- التحقق عبر Zod مع رسائل عربية (`z.config(z.locales.ar())`).
- كل عملية كتابة تُسجَّل في `AuditLog` (المستخدم، العملية، الكيان، قبل/بعد).
- التسلسلات (`Sequence`) تولّد أكواداً غير قابلة لإعادة الاستخدام: `P-0001` للقطع، `S-0001` للأطقم، `INV-00001` للفواتير، ورقم الجرد.

### المسارات

| الملف | النطاق |
|---|---|
| `routes/auth.ts` | دخول/خروج، المستخدم الحالي، تغيير كلمة المرور |
| `routes/users.ts` | CRUD المستخدمين، إعادة تعيين كلمة المرور، تفعيل/تعطيل |
| `routes/settings.ts` | إعدادات المحل (تُقرأ وتُحدَّث كصف واحد id=1) |
| `routes/lookups.ts` | التصنيفات/الموردون/المصانع/البلاد/طرق الدفع/العيارات (حذف ناعم عند الاستخدام) |
| `routes/prices.ts` | سعر الأونصة وسعر الصرف كسجل تاريخي، جدول أسعار الغرام، جلب الأونصة من goldapi.dev، وحالة التحديث التلقائي |
| `routes/items.ts` | قطع وأطقم، أوزان، مكوّنات، تصنيف «طقم» مفروض، مصنّع من قائمة، شراء بالغرام وسعر صرف محفوظ، بحث وتصفية، وإخفاء حقول التكلفة عن البائع |
| `routes/sales.ts` | إنشاء فاتورة مع سياسة ربح/تقريب/صرف خاصة بها، قائمة/تفاصيل، إلغاء للمالك |
| `routes/inventory.ts` | ملخص تقييم المخزون + صفوف الأصناف مع حجب التكلفة/الهامش عن البائع |
| `routes/stocktakes.ts` | فتح جرد، لقطة، تعديل الأسطر، إغلاق، تقرير فروقات |
| `routes/reports.ts` | مبيعات، أرباح، مخزون، سجل أسعار، سجل تدقيق |
| `routes/dashboard.ts` | مؤشرات الصفحة الرئيسية |
| `app.ts` | تركيب middleware والمسارات و`/api/health` و`/api/bootstrap` |

### المعاملات والذرّية

إنشاء البيع، فتح الجرد، الإغلاق، وإعادة تعيين المستخدم تُنفَّذ داخل `prisma.$transaction` لضمان الذرّية.

- إنقاص كمية الصنف عند البيع يتم بـ`updateMany` شرطي (`status=AVAILABLE` و`quantity >= المطلوب`) ثم تحويله إلى `SOLD` عند الصفر؛ هذا يمنع بيع نفس القطعة من طلبين متزامنين.
- إلغاء البيع يغيّر الحالة أولاً بـ`updateMany({ id, status: COMPLETED })`؛ فإن لم يتأثر صف واحد يُرفض الطلب، ثم تُعاد الكميات مرة واحدة فقط.
- إعادة المواد المالية (قيم الأسعار، التكلفة، الهامش) تُقرأ من الخادم، والواجهة لا تعيد حسابها إنتاجياً.

### قواعد الأصناف والقوائم

- `resolveCategoryId` في `routes/items.ts`: إذا كان النوع `SET` يُبحث عن تصنيف «طقم» النشط ويُفرض على القطعة، حتى لو أرسل العميل تصنيفاً مختلفاً. القطعة المفردة تحتفظ بما اختاره المستخدم.
- `resolveManufacturer`: المصنّع يُختار من قائمة `MANUFACTURER`، ويُحفظ `manufacturerId` للعلاقة مع `Lookup`، مع نسخ النص إلى `manufacturer` كمرآة للتوافق مع التقارير والبيانات القديمة. القيمة المعطّلة تُرفض.
- إضافة قيم القوائم: المالك يستطيع إضافة أي نوع؛ البائع يستطيع إضافة `SUPPLIER` و`MANUFACTURER` فقط (إضافة سريعة من نموذج القطعة). بقية الأنواع تبقى للمالك.
- الحذف الناعم يمتد للمصانع: أي مصنع مرتبط بقطعة يُعطَّل بدل حذفه.

## 5. محرك التسعير (`packages/pricing`)

### خط الأنابيب

```ts
computeWeights(input)        // يتحقق من الأوزان ويحدد وزن الأساس
gramPrice24(ounce, fx)      // (سعر الأونصة × الصرف) ÷ 31.1035
karatFactor(karat)          // K ÷ 24
computeItemPrice(input)     // يجمع القيمة + الحجر + الربح + التقريب
```

### ثوابت وقواعد

- `TROY_OUNCE_GRAMS = 31.1035` (قرار توافق مع أمثلة الوثيقة).
- `KARAT_BASE = 24`.
- أساس الوزن: `NET_GOLD` (افتراضي)، `TOTAL`، `MINUS_STONE`، `MINUS_INLAYS`.
- BR-10: حجر له سعر خاص ⇒ يُخصم وزنه دائماً.
- أوزان سالبة أو مجموع حجر/فصوص ≥ الإجمالي ⇒ `PricingError` برسالة عربية.
- الربح: `PERCENT` من (ذهب + حجر)، أو `FIXED` مبلغ ثابت، أو `MANUAL` سعر نهائي (الربح = اليدوي − المجموع).
- في `FIXED` يحدّد `fixedBasis` أساس الضرب: `GRAM` ⇒ `profitValue × basisWeight`، و`PIECE` ⇒ `profitValue × max(1, floor(pieceCount || 1))`؛ الافتراضي `PIECE`. الأطقم تمرّر عدد المكوّنات ذات الوزن الأكبر من صفر، ويُطبَّق التقريب بعد الضرب.
- سياسة كل فاتورة: طريقة الربح وقيمته وخطوة التقريب **ونمط سعر الصرف** (نقدي `CASH` أو صك مصدق `CHEQUE`) تُختار في شاشة البيع، وتُحفظ على صف `Sale` (`profitMode`, `profitValue`, `roundingStep`, `fxMode`, `fxRate`) مع بقاء الإعدادات افتراضيات فقط.
- سعر الصرف المستعمل في الفاتورة يُثبَّت لحظة البيع؛ صرف الصك المصدق مستقل عن صرف النقدي.
- التقريب يُطبَّق **مرة واحدة** على السعر النهائي بخطوة 0/5/10.
- النتيجة تعيد التفصيل كاملاً (غرام 24، غرام العيار، قيمة الذهب، الحجر، الربح، قبل/بعد التقريب) كي تعرضه الواجهة مستقلاً.
- شراء القطعة بالغرام يحسب: `الإجمالي بعملة الشراء = سعر الغرام × وزن الذهب الصافي`، ثم `التكلفة بالدينار = الإجمالي × سعر الصرف` المحفوظ. لا يوجد أي سعر بيع تقديري في مسار الشراء.

### لماذا `decimal.js`

لتجنب أخطاء الفاصلة العائمة في المال والأوزان. التحويل إلى `number` يحدث عند حدود العرض/التخزين فقط.

### التحديث التلقائي لسعر الأونصة

`lib/price-scheduler.ts` يعمل داخل عملية الـAPI نفسها (بلا خدمة منفصلة):

- يبدأ مع `app.listen` في `index.ts` ويتوقف عند `SIGINT`/`SIGTERM`.
- يعمل فقط إذا كان `GOLD_PRICE_PROVIDER=api` و`GOLD_PRICE_REFRESH_MINUTES > 0` والمفتاح مهيأ.
- عند الإقلاع يجلب السعر فقط إذا كان آخر تحديث أقدم من الفاصل (لا تكرار عند إعادة التشغيل).
- كل دورة تنشئ صف `PriceUpdate` بمصدر `API` باسم **أول مالك نشط**، وتكتب تدقيق `AUTO_FETCH_PRICE` يتضمن السعر ووقت المزوّد وعنوان الطلب.
- الأخطاء (شبكة/مفتاح/حصة) تُطبع كتحذير فقط ولا تُسقط الخادم؛ الإدخال اليدوي يبقى متاحاً.
- `GET /prices/table` يعيد `providers.ounce.autoRefresh` و`refreshMinutes`، والواجهة تُعيد الجلب بنفس الفاصل وتعرض شارة «تحديث تلقائي كل N دقيقة».
- **حصة المزوّد:** الخطة المجانية 100 طلب/ساعة؛ 10 دقائق = 6 طلبات/ساعة. لا يُنصح بفاصل أقل من 5 دقائق دون ترقية الخطة.

## 6. التقييم والمخزون

- `lib/valuation.ts` يحسب قيمة الصنف الحالية بأسعار اللحظة مع مراعاة أساس الوزن والإعدادات.
- `GET /inventory/summary` يعيد الإجماليات، التوزيع حسب العيار، و`rows` (صفوف الأصناف) كي يستطيع البائع رؤية المخزون دون الوصول لتقرير المالك.
- إخفاء التكلفة عن البائع يتحكم به `showCostToSeller` في الإعدادات، ويُطبَّق **في الخادم**: حقول `cost` و`margin` تُحذف من `rows` و`byKarat` و`totals` قبل الإرسال، وليس مجرد إخفاء بصري.
- حقول الشراء (`purchaseGramPrice`, `purchasePrice`, `purchaseCurrency`, `purchaseFxRate`, `purchaseCostDinar`) تُحذف أيضاً من استجابات `/items` للبائع عند إخفاء التكلفة.
- عند غياب الأسعار، تُعاد القيم صفراً مع `ready=false` وتعرض الواجهة تنبيهاً بدل أرقام مضللة.

## 7. نموذج البيانات

الجداول الأساسية:

- `User`, `Session` — المستخدمون والجلسات.
- `Setting` — صف واحد لإعدادات المحل.
- `Lookup` — قوائم مرجعية بنوع ومفتاح فريد `(kind, value)`: تصنيفات، موردون، **مصانع**، بلاد، طرق دفع، عيارات. تصنيف «طقم» يُضاف من الـseed.
- `PriceUpdate` — سجل تاريخي لسعر الأونصة/الصرف (لا يُعدَّل)، بمصدر `MANUAL` أو `API` واسم من أدخله.
- `Item`, `ItemComponent` — قطعة أو طقم بمكوّنات، أوزان، حجر/فصوص، حالة، وشراء بالغرام: `purchaseGramPrice`, `purchasePrice` (بعملة الشراء), `purchaseCurrency`, `purchaseFxRate`, `purchaseCostDinar`. المصنّع عبر `manufacturerId` → `Lookup` مع نص مرآة في `manufacturer`.
- `Sale`, `SaleItem` — فاتورة وسطورها (الكمية وسعر الوحدة والإجمالي؛ D-30 يحفظ السعر النهائي فقط)، مع لقطة سياسة الفاتورة: `profitMode`, `profitValue`, `roundingStep`, `fxMode`, `fxRate`.
- `Stocktake`, `StocktakeLine` — جرد ولقطته.
- `AuditLog` — سجل التعديلات.
- `Sequence` — عدادات الأكواد.

الأوزان `Decimal(10,3)` والمبالغ `Decimal(14,2)`، والعلاقات تستخدم `onDelete` مناسباً لحماية السجل التاريخي.

## 8. الواجهة (`apps/web`)

### التوجيه والحراسة

- `app/App.tsx` يعرّف المسارات: `/login` عام، والباقي داخل `AppShell`.
- `Protected` يمنع غير المسجلين ويحفظ مسار العودة.
- `OwnerOnly` يحمي `/reports`, `/settings`, `/users`.
- صفحة غير موجودة افتراضية داخل التطبيق.

### حالة الخادم

- TanStack Query بمفاتيح ثابتة: `['auth','me']`, `['settings']`, `['prices']`, `['items']`, `['inventory']`, `['sales']`, `['stocktakes']`, `['reports', ...]`, `['users']`, `['lookups', ...]`, `['dashboard']`.
- بعد أي كتابة تُبطَّل المفاتيح المتأثرة فقط.
- `lib/api.ts` يوحّد الطلبات، الأخطاء (`ApiError.displayMessage`)، و`qs` لبناء الاستعلامات.

### واجهة المستخدم

- `components/ui/primitives.tsx`: أزرار، حقول، بطاقات، شارات، جداول، تبويبات، مؤشرات.
- `components/ui/overlay.tsx`: نوافذ ومربعات تأكيد.
- `components/ui/toast.tsx`: إشعارات نجاح/خطأ.
- `components/Receipt.tsx`: فاتورة مشتركة بين إنشاء البيع وعرضه.
- RTL كامل عبر `dir="rtl"`، وأرقام لاتينية للقيم المالية، وخط IBM Plex Sans Arabic.
- الثيم فاتح/داكن عبر `data-theme` ومتغيّرات CSS؛ الألوان الذهبية/الفحمية تعبّر عن هوية الذهب.
- `pages/ItemForm.tsx` يضم `LookupPicker` لإضافة مورّد/مصنع سريعاً من نفس النموذج، ويُعطّل التصنيف ويُثبّته على «طقم» عند اختيار النوع طقم.

### المعاينات

`lib/pricing-preview.ts` يستدعي محرك التسعير نفسه في المتصفح لمعاينة سعر الغرام وبطاقة الصنف قبل الحفظ، فلا تنشأ معادلة موازية في الواجهة.

### سياسة البيع وعرض التكلفة

- بطاقة **«سياسة الربح والتقريب»** في `pages/SaleNew.tsx` تُهيّأ من الإعدادات مرة واحدة، ثم تُعدَّل لهذه الفاتورة فقط؛ من ضمنها «أساس الربح الثابت» حين يكون النمط `FIXED`.
- قاعدة الظهور: `showCost = isOwner || settings.showCostToSeller === true`. عند `false` لا تُعرض التكلفة أو الربح/الخسارة في السلة أو الملخص أو نافذة التأكيد.
- مكوّن `ProfitDelta` يعرض `—` عند غياب التكلفة، و`ربح 0` عند تساوي الطرفين، وربحاً أخضر أو خسارة حمراء مع نسبة الفرق من التكلفة.
- صفحة **الإعدادات** تعرض اختيار `fixedBasis` عند `FIXED` وتحفظه كافتراضي؛ القيمة المحفوظة في الفاتورة مستقلة عن تغيير الإعدادات لاحقاً.

## 9. دورة حياة الجرد

```
فتح (OWNER) ──▶ لقطة أوزان/قيم كل صنف متاح
   │
   ├─ تسجيل الوزن المعدود (البائع أو المالك) — PATCH لكل سطر
   ├─ تعليم قطعة كغير موجودة (present=false)
   │
   ▼
إغلاق (OWNER) ──▶ يصبح السجل نهائياً (BR-14)
```

- يُسمح بجرد مفتوح واحد فقط؛ فتح ثانٍ يُرفض.
- `weightDiff = countedWeight − expectedWeight` يُحسب في الخادم.
- تقرير الفروقات يقسّم النتائج إلى ثلاث مجموعات **منفصلة**: غير موجودة، أوزان مختلفة (للقطع الموجودة فقط)، وأصناف جديدة لم تُسجَّل في اللقطة.
- الواجهة تحفظ الوزن عند مغادرة الحقل، وتحدّث الفروقات فوراً، وتُظهر تقدّم العدّ.

## 11. الأمان

- كلمات المرور مُجزّأة، والجلسات في قاعدة البيانات وليست JWT قابلة للتزوير.
- صلاحيات على مستوى المسار + تحقق ملكية الموارد.
- تحقق مدخلات صارم على كل مسار (Zod) ورسائل أخطاء عربية دون كشف تفاصيل داخلية في الإنتاج.
- `helmet`, `cors` مقيّد بـ`APP_ORIGIN`؛ في الإنتاج يُسمح بأصل الواجهة فقط، وفي التطوير تُضاف أصول `localhost` المحلية.
- `originGuard` يرفض الطلبات المعدِّلة القادمة من أصل غير مسموح (حماية CSRF إضافية).
- حدود محاولات الدخول: 30/10 دقائق لكل IP و8/10 دقائق لكل حساب، مع `Retry-After` وتصفير العدّاد بعد الدخول الناجح. وحد لجلب الأسعار اليدوي من المزوّد (20/5 دقائق لكل مستخدم) لحماية حصة المفتاح. التحديث التلقائي لا يمر بهذا الحد لأنه محكوم بالفاصل الزمني (6/ساعة افتراضياً).
- إخفاء التكلفة والهامش وحقول الشراء يحدث في الخادم حسب الدور وإعداد `showCostToSeller`.
- تحقق صارم من معاملات الاستعلام (أرقام موجبة، تواريخ صالحة، طول الكيان، حد `take`) ومن رمز العملة (حروف لاتينية فقط ثم تحويله إلى أحرف كبيرة).
- تدقيق كامل للعمليات الحساسة (بيع، إلغاء، أسعار، شراء، إعدادات، مستخدمون)، دون تسجيل كلمات المرور.

## 12. التشغيل والتحقق

- MySQL محمول: `tools/mysql-init.ps1` مرة واحدة، ثم `mysql-start.ps1` / `mysql-stop.ps1`.
- مخطط Prisma يُطبَّق بـ`npm.cmd run db:push` (لا يوجد مجلد `migrations` بعد)؛ `npm.cmd run db:migrate` متاح لإنشاء أول ترحيل عند الحاجة.
- `db:reset` يعيد البناء والبيانات الأولية — للاستعمال الحذر فقط.
- سلسلة التحقق المعتمدة: `npm.cmd test`، `npm.cmd run typecheck`، `npm.cmd run build`، ثم `npm.cmd run test:integration` و`npm.cmd run test:stress` على خادم حي وMySQL مهيأ.
- تفاصيل الأوامر في `README.md`، وقائمة التحقق الكاملة في **[SYSTEM_SPECIFICATION.md](SYSTEM_SPECIFICATION.md)**.

## 13. حدود معروفة وتوسعات مستقبلية

- مزوّد سعر الأونصة (goldapi.dev) مفعّل عند إضافة مفتاح API، ويعمل بتحديث تلقائي مجدول داخل الخادم؛ سعر الصرف ما زال يدوياً، والبنية جاهزة لمزوّد صرف تلقائي.
- الطباعة تتم عبر طباعة المتصفح؛ لا توليد PDF من الخادم (نسخة PDF من هذا الدليل تُولَّد يدوياً وقت التوثيق).
- لا صور/QR/حجز أو لغات إضافية (خارج النطاق).
- محل واحد فقط (لا multi-tenant).
- لا إشعارات خارج التطبيق (بريد/واتساب).

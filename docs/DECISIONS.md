## 4. محرك التسعير

```
gram24 = (سعر الأونصة × سعر الصرف) ÷ 31.1035
سعر غرام العيار K = gram24 × (K ÷ 24)
قيمة الذهب = وزن أساس الاحتساب × سعر غرام العيار
السعر النهائي = (قيمة الذهب + سعر الحجر) + الربح ثم التقريب
```

| القرار | التفصيل |
|---|---|
| ثابت أونصة تروي = `31.1035` | مطابق حرفياً لأمثلة الوثيقة (جداول 4.1 و4.2)؛ الفرق عن القيمة الفيزيائية الدقيقة أقل من 0.001%. |
| أساس 24 قيراط | `KARAT_BASE = 24`؛ معاملات 18 = 0.750، 21 = 0.875، 24 = 1.000. |
| عرض سعر الغرام مستقلاً | سعر كل عيار يُعرض في صفحة الأسعار وبطاقة الصنف، لا يُخفى داخل سعر القطعة النهائي. |
| أساس الوزن | `NET_GOLD` افتراضي (خصم الحجر والفصوص)، مع بدائل: `TOTAL`, `MINUS_STONE`, `MINUS_INLAYS` حسب الإعدادات. |
| BR-10 | أي حجر له سعر خاص يُخصم وزنه دائماً، حتى لو كان خيار الخصم مغلقاً. |
| أوزان غير صالحة | مجموع الحجر/الفصوص ≥ الإجمالي أو وزن سالب ⇒ خطأ تسعير برسالة عربية. |
| أنماط الربح | نسبة من (ذهب + حجر)، مبلغ ثابت، أو سعر نهائي يدوي (الربح = اليدوي − المجموع). |
| أساس الربح الثابت | عند `FIXED` يختار `fixedBasis` بين `GRAM` (`profitValue × basisWeight`) و`PIECE` (`profitValue × max(1, floor(pieceCount || 1))`)؛ الافتراضي `PIECE`. الطقم يمرّر عدد مكوّناته ذات الوزن الأكبر من صفر، والتقريب يأتي بعد الضرب. |
| التقريب مرة واحدة | على السعر النهائي فقط بخطوة 0/5/10، بعد إضافة الحجر والربح. |
| النتيجة تفصيلية | المحرك يعيد gram24، سعر غرام العيار، قيمة الذهب، الحجر، الربح، وقبل/بعد التقريب كي تعرضها الواجهة. |

## 5. الأسعار

| القرار | التفصيل |
|---|---|
| سعر الأونصة: يدوي + goldapi.dev | الإدخال اليدوي متاح دائماً، وزر «جلب من goldapi.dev» يستدعي `GET /price/XAU/USD` من `https://goldapi.dev/api/v1` ويحفظ الصف بمصدر `API`. |
| تحديث تلقائي مجدول | `GOLD_PRICE_REFRESH_MINUTES` (افتراضي 10، و0 يعطّله) يشغّل مجدولاً داخل الخادم يجلب السعر ويحفظه باسم أول مالك نشط. الفاصل 10 دقائق = 6 طلبات/ساعة مقابل حد 100/ساعة في الخطة المجانية. |
| لا تكرار عند الإقلاع | عند بدء الخادم يُفحص آخر تحديث؛ إن كان داخل الفاصل لا يُجلب سعر جديد، حفاظاً على الحصة ومنع الصفوف المكررة. |
| رابط التوثيق في الواجهة | صفحة الأسعار تُظهر رابط <https://goldapi.dev/docs> وحالة تهيئة المفتاح، حتى يعرف المستخدم كيف يجد مفتاحه أو يجدّده (الرابط مخفٍ على الجوال لتقليل الفوضى). |
| توضيح أن السعر للخام | نص موحّد `RAW_GOLD_PRICE_NOTE` في `lib/copy.ts` يظهر في صفحة الأسعار والرئيسية و`title` شرائح الهيدر؛ المصنعية والمصنع والمنشأ والشحن تُضاف عند تسعير القطعة لا في جدول الأسعار. |
| المفتاح في الخادم فقط | `GOLD_PRICE_API_KEY` يُقرأ في `apps/api/.env` ولا يُرسل للمتصفح؛ الواجهة تتلقى فقط `configured: true/false`. |
| فشل المزوّد لا يعطّل العمل | أخطاء 401/403/429/شبكة/مهلة تتحول لرسالة عربية واضحة، ويبقى الإدخال اليدوي هو المسار الاحتياطي. |
| حد جلب الأسعار | 20 عملية/5 دقائق لكل مستخدم للجلب اليدوي لحماية الحصة؛ التحديث التلقائي محكوم بالفاصل الزمني ولا يمر بهذا الحد. |
| سعر الصرف يدوي | `FX_PROVIDER=manual`؛ إدخال الأونصة والصرف معاً في صفحة واحدة، مع معاينة فورية لأسعار العيارات. |
| المعاينة قبل الحفظ | صفحة الأسعار تحسب أسعار العيارات لحظياً، وتميّز «معاينة غير محفوظة» عن «محفوظ». |
| واجهة تتبع المجدول | `/prices/table` يعيد `autoRefresh` و`refreshMinutes`، والواجهة تُعيد الجلب بنفس الفاصل وتعرض شارة واضحة بدل أرقام معلّقة. |
| السعر اللحظي في التقييم | المخزون والتقارير تُقيَّم بآخر سعر محفوظ؛ عند غيابه تُعرض قيم صفرية مع `ready=false` وتنبيه بدل أرقام مضللة. |
| تنبيه قدم السعر | `priceStaleHours` (افتراضي 2) يُظهر تحذيراً في الرئيسية عند تجاوز المدة. |

## 8. المخزون والبيع

| القرار | التفصيل |
|---|---|
| قطعة أو طقم | الطقم له مكوّنات بأوزان وعيارات؛ الوزن الإجمالي ووزن الذهب يُجمَعان من المكوّنات. |
| تكلفة الشراء | تُحفظ بعملتها وسعر صرفها (`purchaseCurrency`, `purchaseFxRate`) لحساب الربح لاحقاً. الشراء بالغرام يحفظ `purchaseGramPrice` وإجمالي القطعة بعملة الشراء وتكلفتها بالدينار. |
| لا سعر بيع في شاشة الشراء | إدخال الشراء يعرض فقط تكلفة الشراء وإجماليها بعملة الشراء والدينار؛ سعر البيع يُحسب عند البيع من سعر السوق وسياسة الفاتورة. |
| سياسة كل فاتورة | طريقة الربح وقيمته وخطوة التقريب ونمط الصرف (نقدي/صك مصدق) تُختار في شاشة البيع وتُحفظ على `Sale`؛ الإعدادات افتراضيات فقط ولا تُعدَّل عند البيع. |
| صرف الصك المصدق مستقل | لكل فاتورة صرف نقدي وصرف صك؛ اختيار طريقة دفع تحتوي «صك» يبدّل النمط إلى `CHEQUE` تلقائياً، ويُحفظ السعر المستعمل مع الفاتورة. |
| منع البيع المزدوج | إنقاص الكمية ذرّي بـ`updateMany` شرطي، وإلغاء البيع يغيّر الحالة أولاً ثم يعيد الكميات مرة واحدة. |
| D-30 — السعر النهائي فقط | سطر البيع يحفظ الكمية وسعر الوحدة والإجمالي، دون تفصيل معادلة التسعير داخل الفاتورة. |
| بيانات الزبون اختيارية | الاسم والهاتف اختياريان (D-25). |
| إلغاء البيع للمالك | يستعيد الأصناف إلى `AVAILABLE` ويسجّل السبب والوقت والمنفّذ، ويُبقي الفاتورة في السجل. |
| صفوف المخزون للبائع | `GET /inventory/summary` يعيد `rows` إضافةً إلى الإجماليات، كي يرى البائع القطع المتاحة دون فتح تقرير المالك. |
| عرض التكلفة والربح في البيع | القاعدة `showCost = isOwner || settings.showCostToSeller`؛ عند `false` تُخفى الأرقام في السلة والملخص ونافذة التأكيد. `ProfitDelta` يعرض ربحاً أو خسارة مع نسبتهما من التكلفة، أو `—` عند غياب التكلفة. الأرقام للعرض فقط والخادم مصدر السعر النهائي. |
| اختيار أساس الربح في شاشة البيع | يظهر «أساس الربح الثابت» فقط مع `FIXED`؛ القيمة الابتدائية من `settings.fixedBasis`، وتُحفظ في الفاتورة مستقلة عن الإعدادات. |
| التقييم لحظي | قيمة المخزون تُحسب بأسعار اللحظة وأساس الوزن الحالي، لا بسعر الشراء. |

| تحقق رمز العملة | حروف لاتينية 2–8 فقط، ثم يُحوَّل تلقائياً إلى أحرف كبيرة لتوحيد العرض والتقارير. |
| قوائم مرجعية | تصنيفات، موردون، **مصانع/علامات**، بلاد، طرق دفع، عيارات — CRUD عبر `/lookups`. |
| المصنّع علاقة + نص مرآة | `Item.manufacturerId` يربط بقائمة `MANUFACTURER`، ويُنسخ الاسم إلى `manufacturer` للتقارير والبيانات القديمة. التعديل المستقبلي لاسم المصنع في القائمة لا يغيّر تاريخ الأصناف تلقائياً. |
| تعطيل بدل حذف | أي قيمة مستعملة تُعطَّل، وتبقى السجلات التاريخية سليمة؛ يشمل ذلك المصانع. |
| الأكواد | تلقائية أو يدوية حسب `codeMode`؛ التلقائي يستعمل `Sequence`. |

## 12. قرارات تشغيلية

| القرار | التفصيل |
|---|---|
| منافذ التطوير | API على `4000` والواجهة على `5173` مع proxy لـ`/api`. |
| `npm.cmd` على Windows | سياسة تنفيذ PowerShell تمنع `npm.ps1` و`npx`. |
| بدء التشغيل | `mysql-start.ps1` ثم `npm.cmd run dev`؛ الإيقاف `mysql-stop.ps1`. |
| النسخ الاحتياطي | الأمر البسيط `npm.cmd run db:backup` ⇒ `tools/backup-db.mjs` ينشئ SQL مؤرّخاً في `backups/` دون إيقاف MySQL أو إدخال كلمة مرور. نسخ `tools/mysql/data` يبقى متاحاً عند إيقاف الخادم. |
| `db:reset` | `prisma db push --force-reset --skip-generate` ثم `seed.ts` (لعدم وجود migrations). |
| الاختبارات | `npm.cmd test` (28 اختباراً)، و`npm.cmd run typecheck` للحزم الثلاث، و`npm.cmd run build` للإنتاج. |
| الفحصان التكاملي والحِمل | `npm.cmd run test:integration` و`npm.cmd run test:stress` متاحان في الجذر، ويحتاجان خادماً حياً على `localhost:4000` وMySQL مهيأ؛ لا يعملان في بيئة معزولة. |
| سكربت الترحيل | `npm.cmd run db:migrate` ينشئ أول ترحيل عند الحاجة، لكن المسار التشغيلي المعتمد ما زال `db:push` لغياب مجلد `migrations`. |
| تجهيز مزوّد الصرف | بنية `FX_API_URL`/`FX_API_KEY` موجودة، والتفعيل لاحق عند اختيار مزوّد صرف موثوق. |
